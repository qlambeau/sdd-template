# ADR-005: Multi-Agent Orchestration Topology

## Context

The SDD workflow (`specs/SDD_WORKFLOW.md`) defines twelve mapped skills and a
promote-only artifact lifecycle. Today a single conversational agent loads
each skill sequentially. This causes:

- Context pollution: interview history, spec prose, implementation output, and
  verification logs accumulate in one session.
- No per-stage permission boundaries: the interview agent has the same powers
  as the implementer.
- No automation: every stage must be driven by hand.

We want a multi-agent setup: a primary orchestrator agent managing specialized
subagents (in opencode, `.opencode/agents/`), each working in its own context.
The filesystem already acts as shared state (artifact files with frontmatter
statuses), so agents need no inter-agent channel; packets are the handoff.

Human oversight remains required: `ADR-002` mandates promote-only status
transitions with human confirmation, and blocking questions must stop for a
human (`AGENTS.md` operating rules). Therefore full-pipeline automation is out
of scope; gated clusters are in scope.

## Decision

Adopt an **orchestrator + stage-subagent topology** with **gate clusters**:

1. **Orchestrator** (`sdd-orchestrator`, primary agent): knows the lifecycle
   and cluster sequence, delegates stage work, owns all `promote-artifact`
   invocations and human confirmations. Its Task-tool permissions allow only
   `sdd-*` subagents (and read-only exploration); it never edits artifacts or
   code directly.

2. **Stage subagents** (one per discipline, each in its own context):

   | Subagent          | Mapped skills                                  | Permissions posture             |
   | ----------------- | ---------------------------------------------- | ------------------------------- |
   | `sdd-product`     | `create-prd`, `refine-epic`                     | interview + draft writing       |
   | `sdd-story`       | `refine-user-stories`, `user-story-to-gherkin`   | interview + draft writing       |
   | `sdd-contract`    | `create-requirements`, `create-design`, `create-tasks` | interview + draft writing |
   | `sdd-implementer` | `implement-feature`                             | edit + bash, no interviewing    |
   | `sdd-verifier`    | `verify-feature`                                | edit (evidence) + bash gates    |
   | `sdd-releaser`    | `record-release`, `triage-observation`          | edit specs only                 |
   | `sdd-reviewer`    | read-only spec-ready predicate validation       | read-only                       |

3. **Gate clusters** — the orchestrator pauses for explicit human confirmation
   after each cluster; subagents run freely inside a cluster:

   - Cluster 1 (product intent): `create-prd`, `refine-epic`
   - Cluster 2 (story & behavior): `refine-user-stories`, `user-story-to-gherkin`
   - Cluster 3 (contract & plan): `create-requirements`, `create-design`, `create-tasks`
   - Cluster 4 (build & verify): `implement-feature`, `verify-feature`
   - Cluster 5 (release): `record-release`, `triage-observation`

   Cluster boundaries align with the spec-ready predicate: cluster 3 ends with
   `sdd-reviewer` validating spec-ready before the orchestrator promotes the
   packet and enters cluster 4.

4. **Skills remain the single source of process truth.** Subagents are thin
   permission/context wrappers that invoke their mapped skills via the skill
   tool. `§Skill Mapping` conformance is preserved: no artifact is created or
   status advanced outside a skill. Subagent prompts forbid manual status
   transitions, forbid writing outside their skill's mapped outputs, and
   require stopping to report blocking questions instead of inventing answers.

5. **The packet on disk is the handoff.** Subagents are stateless between
   clusters; each enters with a fresh context and reads only the packet files
   it needs.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Thin orchestrator delegating to generic subagents with inlined skill instructions | No per-stage permission isolation or naming; skill instructions duplicated in prompts and drift from `SDD_WORKFLOW.md`. |
| Full-pipeline automation with reviewer agent replacing human gates | Violates `ADR-002` promote-only human confirmation and the blocking-question rule. |
| Plugin-based enforcement only | Enforces rules but does not provide the agent topology or context isolation. |
| Global agent definitions (`~/.config/opencode/agents/`) | Workflow-specific agents would leak into unrelated projects; topology should travel with the template repo. |

## Consequences

### Positive

- Each stage runs in a clean, isolated context; long interviews no longer
  pollute implementation context.
- Permission boundaries match constitutional risk: implementer alone can edit
  code and run gates; reviewer is provably read-only.
- Cluster gates keep a human at every approval point while automating
  intra-cluster mechanics.
- Skills stay authoritative; agent definitions remain small and stable.

### Negative Or Tradeoffs

- Agent topology files (`.opencode/agents/`) become a second place workflow
  mechanics are described; they must stay derivative of `SDD_WORKFLOW.md`.
- Orchestrator relays gate confirmations, adding one delegation hop per stage.
- Subagent context isolation means each stage re-reads the packet; small cost
  per stage, but large packets need disciplined file scoping.

## Follow-Up Actions

- Create the agent definitions under `.opencode/agents/` per the table above.
- Document the topology in `AGENTS.md` as informational, deferring to
  `SDD_WORKFLOW.md` per the normative-precedence rules.
- Verify the orchestrator cannot invoke non-`sdd-*` subagents and that gate
  pauses surface correctly before relying on the topology.
